Which checks fire — entry

Where users enter the waterfall

The brief describes one front door. There are two, and the second one is undocumented.

The documented design is broadly the design that runs — but three things in it are not what the brief describes. There is a second front door. An Idology pass does not always end the journey.

Method note: with no per-check timestamps, order above is inferred from column co-occurrence, kyc_source attribution and Idology's near-universality, not observed directly — and a null provider column is only an upper bound on “did not run,” not a guarantee, since at least 11,695 users carry a reviewer comment naming a check whose result was never written back.

In what order

The order checks fire in, and the one place it breaks

The documented order — L1 Idology, then an SSN or non-SSN branch, then manual review — holds as a dependency order: 96.3% of users are checked by Idology first, every secondary provider fires overwhelmingly on users who already have an Idology result, and manual review is the only check that appears alongside all the others. Nothing in the data contradicts that shape.

One documented rule does not hold. The brief says a user who passes Idology is verified and exits the waterfall. 130,713 users passed Idology and had LexisNexis run anyway, and 57,822 of them failed that second check and were verified regardless — a 99.9% verification rate for the group. So L2 is running in a non-blocking position for some passing users: it costs a provider call and returns a result nobody acts on.

This is also why the L1 pass rate and the L1 exit rate are different numbers. 84.80% of the book passes Idology; only 79.57% passes it and stops there. The 5.23% gap is precisely this non-blocking check. Quoting the pass rate as though it were the exit rate merges the two and hides the finding.

How users route — SSN vs non-SSN

How users route between the SSN and non-SSN paths

This is the decision the waterfall is built around. For 288,028 users who failed Idology, here is where they actually went.

How users route — the crossover rule

The design states that if an SSN-path provider surfaces a secondary non-SSN issue, the user moves to the non-SSN track. That rule is real — and it leaks in both directions.

LexisNexis returned FAIL 19.47% 6,963 of 35,761 crossed over
LexisNexis returned PASS 9.50% 1,633 of 17,197 crossed over
Persona-SSN leg only 0.45% 9 of 2,015 crossed over
Directionally confirmed, mechanically leaky. A failed SSN check is twice as likely to cross over as a passed one, which is the documented rule showing up in the data. But the rule does not explain a 9.5% crossover rate on users whose SSN check passed, and it is effectively absent from the Persona-SSN leg, where 9 users in 2,015 ever cross. The crossover is implemented on the LexisNexis leg and essentially not implemented on the other.

What this cannot establish: direction. With no timestamps, a user holding both a LexisNexis and an ACRO result is evidence that both checks ran — not that one preceded the other. I read these 8,605 as SSN→non-SSN because that is the documented direction and because the reverse is much rarer in the population (7.7% of ACRO failures also carry an SSN check, against 19.5% the other way). That is an inference from asymmetry, not a measurement.

One documented rule is not reproducible at all. The brief routes “older accounts” to legacy Persona-SSN. Tested both readings: mean age is 34.9 for Persona-SSN users against 34.7 for everyone else, and the route fires on 0.42–0.44% of users in every enrolment year including 2026 — flat, where a legacy route being wound down would decay. Neither age nor vintage drives it. The field that does is not in this extract.

ProviderA carries nine times the volume and is dominated by users who never saw Idology — it is the side door from Step 0. ProviderB is small, almost entirely post-Idology-failure, and three times more likely to be paired with Persona-SSN — it is the SSN-path secondary the design describes. Same brand, same column, opposite roles.

Summary

Documented design vs the system that runs

Documented

Idology is the primary check for every user.

Observed

93,319 users (3.71%) never see it and are cleared by ProviderA LexisNexis, which passes ~100%.

SECOND DOOR
Documented

Pass Idology ⇒ verified, exit the waterfall.

Observed

130,713 passed and had LexisNexis run anyway; 57,822 failed it and verified regardless. Pass rate 84.80%, exit rate 79.57%.

NON-BLOCKING
Documented

Fail Idology ⇒ log the reason and route by SSN vs non-SSN.

Observed

43.73% of failures (125,941) reach neither path. 101,162 of them reach no check at all and recover 12 people.

MAIN DEFECT
Documented

If an SSN provider surfaces a non-SSN issue, move the user to the non-SSN track.

Observed

Real: 19.47% crossover after a LexisNexis FAIL vs 9.50% after a PASS. But absent from the Persona-SSN leg (0.45%).

PARTIAL
Documented

SSN path sends standard users to LexisNexis and older accounts to legacy Persona-SSN.

Observed

No age signal (34.9 vs 34.7) and no vintage signal (flat 0.42–0.44% every year).

NOT REPRODUCIBLE
Documented

The two LexisNexis routes are different integration paths.

Observed

Confirmed, and stronger than stated: ProviderA is primary-position, ProviderB is secondary. They are not interchangeable.

CONFIRMED
Documented

A null provider value means the check did not run.

Observed

False for at least 11,695 users whose reviewer comment names a provider whose column is null. Checks run off-instrument.

CONTRADICTED
Denominators used on this page. The book is 2,515,155 users (2,515,262 less 107 flagged test accounts). Idology outcome rates use 2,420,972 — the users Idology actually ran for. Routing shares use 288,028 — Idology failures excluding test accounts; the all-in figure is 288,134. Two integrity notes: 2 of 149,364 ProviderA_Lexis_Nexis rows credit that source without a matching PASS in the column, and 21 users enter by paths too small to chart. Neither moves any figure above.
